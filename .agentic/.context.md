# Project Context

## Overview
Agentic is a Flutter desktop application that provides a multi-backend LLM chat interface and a local Python orchestrator that gives models real filesystem and command-execution tools, turning them into coding assistants on the user's machine.

## Operative Nature
- **Purpose**: Let users chat with multiple LLM providers through one unified UI, and optionally run a local orchestrator that lets the model read/write files, run commands, search code, and validate builds on the local machine.
- **Primary Use Cases / User Flows**:
  - Configure a backend (HuggingFace, Ollama, Groq, Gemini, OpenRouter, or GitHub Models) with an API key or local server.
  - Start a conversation, send prompts, and receive Markdown-rendered answers with syntax highlighting.
  - Enable the orchestrator to let the model act on a selected project folder with filesystem tools.
  - Review audit logs of every tool call.
- **Key Features**:
  - Multi-backend LLM support (HuggingFace Inference, Ollama local/cloud, Groq, Gemini, OpenRouter, GitHub Models).
  - Local Python orchestrator with read/write/patch/search/run-command/git tools.
  - Task-flow protocol (plan → execute → report) with progress tracking.
  - Persistent SQLite conversation history, conversation grouping, and context summaries.
  - Markdown rendering with syntax highlighting and a dark developer theme.
  - Desktop drag-and-drop file attachments.
  - Secure storage for API keys.
  - Sandbox mode restricting the orchestrator to read-only operations.
  - Audit logging of tool calls.
  - Configurable filesystem include/exclude filters.
  - Database connections (SQLite, MariaDB, SQL Server) queryable by the model.
- **Target Users / Domain**: Developers and technical users who want a local AI coding assistant and multi-provider chat workbench.

## Technical Nature
- **Tech Stack**: Backend (Python 3.10+, stdlib plus `requests`); Frontend (Flutter/Dart, SDK >= 3.3.0, Flutter >= 3.19.0).
- **Architecture & Layers**:
  - Flutter UI (`lib/`) manages chat state, persistence, backend services, and launches the Python orchestrator as a subprocess.
  - Python orchestrator (`bin/`) is a modular tool-registry-based agent loop. `bin/orchestrator.py` is a thin CLI shim; the implementation lives in `bin/agent/` (backends, core, loop, tools, utils, prompts).
  - Interactive protocol: the Flutter client writes one JSON object per line to the orchestrator's stdin (`{"prompt": "...", "new_session": true|false}`); the orchestrator writes the full response to stdout followed by a line containing `__RESPONSE_END__`; diagnostics go to stderr.
- **Key Modules & Responsibilities**:
  - `lib/services/`: LLM backend clients (Groq, HuggingFace, Ollama, OpenRouter, GitHub Models, local LLM), orchestrator manager, project service, secure storage, chat processing, context summaries.
  - `lib/data/`: SQLite database, models, repositories.
  - `lib/ui/`: screens and widgets.
  - `lib/core/`: constants, theme, utils, task queue.
  - `lib/statemanagement/`: state manager, streams, method data/listener.
  - `bin/agent/backends/`: provider backends and rate limiting.
  - `bin/agent/core/`: security policy and core agent logic.
  - `bin/agent/loop/`: run loop and task protocol.
  - `bin/agent/tools/`: tool registry and tool implementations.
  - `bin/agent/utils/`: bootstrap, IO protocol, and shared helpers.
- **Data Models / Persistence**: SQLite via `sqflite` (with `sqflite_common_ffi` on desktop) for conversations, messages, and related state. API keys are stored in platform secure storage (`flutter_secure_storage`).
- **API / Endpoints**: No first-party HTTP server. The Flutter app talks to external LLM REST APIs directly and to the local Python orchestrator over stdin/stdout using the JSON-lines protocol described above. The orchestrator can also be run standalone with CLI flags such as `--backend`, `--hf-token`, `--model`, `--interactive`, `--install-deps`, and `--filters-config`.
- **Build & Run**:
  - Flutter app: `flutter pub get` then `flutter run` (desktop targets: Windows, macOS, Linux; mobile/web scaffolding also present).
  - Orchestrator dependencies: `python bin/orchestrator.py --install-deps` (or via Settings → Install dependencies).
  - Standalone orchestrator: `python bin/orchestrator.py --hf-token YOUR_TOKEN --interactive`.
- **Coding Standards**: No explicit style guide detected. Flutter code uses `flutter_lints`; Python code is linted/formatted with `ruff` in the agent workflow.
- **Testing**: Flutter tests use `flutter_test`; Python tests use `pytest` and live in `tests/` (context, message, reasoner, state, token counter, tool executor, tool registry, tool schema).

## Project Structure
- **Directory Layout**:
  - `lib/` — Flutter/Dart application source (core, data, services, statemanagement, ui, utils).
  - `bin/` — Python orchestrator and its `agent/` package, plus `orchestrator.py`, `orchestrator_base.py`, `orchestrator_multi.py`, and `requirements.txt`.
  - `tests/` — Python pytest suite.
  - `configs/` — runtime configuration such as `prompts_config.xml`.
  - `chats/` — chat-related artifacts (e.g. `modifiche.txt`).
  - `logs/` — application and orchestrator audit logs.
  - `installer/` — Inno Setup script and built Windows installer.
  - `android/`, `ios/`, `linux/`, `macos/`, `web/`, `windows/` — platform scaffolding.
  - `.agentic/` — agent metadata, temporary helper scripts, and this context file.
  - `.github/` — issue and pull request templates.
- **Dependencies**:
  - Flutter: `dio`, `sqflite`, `sqflite_common_ffi`, `path`, `path_provider`, `flutter_secure_storage`, `uuid`, `flutter_markdown`, `flutter_highlight`, `highlight`, `file_picker`, `desktop_drop`, `cross_file`, `html`, `markdown`, `cupertino_icons`.
  - Python: `requests` (>= 2.31.0).
